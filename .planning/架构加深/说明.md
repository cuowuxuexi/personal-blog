# 架构加深说明

2026-08-24 看过近期改得最多的代码之后写下的总说明。用大白话讲：现在哪里别扭、不改会怎样、为什么不是网站坏了、六条各是什么、建议先写哪份提案。

本文件只说明，不定怎么改。每条怎么改，另写优化提案，写之前先把边界问清楚。

## 先说结论

这六条都是真摩擦，值得各写一份提案。它们说的不是「页面打不开」，而是「以后你再发周记、再改发布、再加一页投研时，会不会改一处就够」。

不要一次全改。先把话说清楚，批准一条再动一条。

已经够好、提案里也会写「别动」的：周记和历程怎么从文章生成目录、公众号预览怎么渲染、国内站怎么上传、构建探针对外只说「构建」这一件。

仓库里已有一份模块化计划（阶段 3、阶段 5）和这六条大部分重叠。本轮不是另起一套方向，是把疼点讲成人话，再逐条写成能审批的提案。

## 几个词，只用这一次

后面提案会用到这几个说法，这里用大白话钉死：

| 说法 | 大白话 |
| --- | --- |
| 模块 | 一块有门口、有内部的代码。可大可小。 |
| 接口 | 别人要用它，必须记住的全部规矩：怎么叫、先做什么、会怎样失败。 |
| 实现 | 门里面怎么干活。 |
| 浅 | 门口规矩几乎和里面一样多。说明书比干活还厚。 |
| 深 | 你只说一件事，麻烦在里面办完。 |
| 接缝 | 可以换一种干法、而不用改调用方的那个位置。 |
| 适配器 | 插在接缝上的具体干法。比如真推 Git，测试里用假推。 |
| 泄漏 | 本该只住在一处的规矩，跑到别的文件里又写一遍。 |
| 局部性 | 出错、改动、测试都集中在一个地方。 |
| 杠杆 | 学一次门口规矩，很多地方都能用。 |

删除测试：想象把这块删掉。如果麻烦跟着消失，它只是过路的，不值得加深。如果麻烦散到好几个调用方，它值得留，而且值得加深。

## 你平时会碰到什么

发一期周记或历程：面板里写、预览、确认、等国内站和海外站对上。

加一张研究地图或一份标的档案：改文章，还要改侧栏，往往还要改总览页上的清单。

改发布面板上的一个按钮或一种失败提示：常常要进一份一千多行的总文件。

这三件事对应下面最靠前的几条。

## 六条分别是什么

### 1. 发布任务捆成一坨

你点「确认发布」，一次做完提交、推送、部署、再去对线上对不对。更别扭的是：页面去问「现在到哪一步了」，这一问也可能偷偷继续对线上。

出错时很难分清：是没推上去、国内站没跟上，还是预览其实已经好了。以后你只想改「怎么核对国内站」，也得翻整坨发布代码。

不改的后果：发布一出问题，人和程序都要猜「问进度」有没有顺便干活。

这条最近改得最多，而且门口在撒谎。建议第一份提案写它。

### 2. 「草稿」其实立刻落盘

面板里保存，名字叫草稿，实际马上改仓库里的 Markdown。旁边还有早年改目录、改侧栏的旧刀法。现在发布已经不走那条路，测试却还在养着。

你日常能用。别扭在名字骗人，死人代码还占着接口。

不改的后果：以后谁改保存，容易踩那些已经没人调用的函数。

### 3. 哪些文件能发，写了三遍

「周记在哪、历程图在哪、投研不许从面板发」——内容目录里写过，范围检查又写，校验再写。

不改的后果：你挪目录或加一种可发内容，漏改一处，就可能把不该发的发出去，或把该发的拦住。

### 4. 面板界面一个大管家

为了好测，拆出一些小助手，但顺序、脏标记、恢复、发布仍堆在总文件里。小助手自己没藏多少规矩，规矩在总管家怎么叫它们。

不改的后果：改一个字段或按钮，仍要读整份总调度。

### 5. 投研结构还在手写两遍

加研究地图或标的档案：侧栏写一次，总览页再写一次。周记已经不用这样——正文写在文章里，目录构建时自动长出来。投研还没接上。

不改的后果：投研页越多，漏改侧栏或总览的概率越大。这不是把博客做成私有投研的镜子，只是公开目录少抄一遍。

### 6. 文章开头解析器有三份

标题、日期、修订日这类文头，目录一份、面板一份、旧日记一份，规则略有差别。

今天看不出来。哪天加一个新字段，三份对不上，就会「这边认、那边当没看见」。

## 建议顺序

1. 发布任务  
2. 工作区改写  
3. 发布范围  
4. 面板界面  
5. 投研投影  
6. 文头解析  

前三条是你现在发内容就会碰到、或一改就容易漏。第 4 条是下次改面板最迷路的地方。后两条是加东西时再还的债。

## 和已有决定的关系

- 不重开「博客不是私有投研镜子」。第 5 条只投影公开结构。
- 不重开「正文在 Markdown，目录关系用构建投影」。第 5 条是把投研半边做完。
- 持仓公不公开仍由你决定，本轮不谈。
- 发布仍要你自己预览并确认。拆模块不是改成自动发布。
- 面板仍然不能创建、重命名、删除历程的具名篇章。

## 接下来怎么走

每条先问几件只有你能定的事，再写成一份优化提案：要改什么、不改什么、改完你怎么验收、和别的条怎么错开。

批准提案不等于马上改代码。要动手时再说。
